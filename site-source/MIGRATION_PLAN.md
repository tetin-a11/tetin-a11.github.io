# tetin-a11.github.io サイト刷新手順

対象リポジトリ: `tetin-a11/tetin-a11.github.io`  
公開ブランチ: `main`  
新サイト: 「できるかな魔改造」

## 基本方針

現在の公開サイトを直接上書きしない。旧サイトを複数の方法で保存し、刷新用ブランチで新旧ファイルを統合してから `main` へ反映する。

GitHub Pagesで公開するのは新サイトの `dist/` の内容とする。ただし、現在のルートにあるドメイン・広告・Google認証用ファイルと既存サブサイトは維持する。

## 既存ファイルの取り扱い

| 現在の項目 | 移行時の扱い | 理由 |
|---|---|---|
| `CNAME` | 内容を確認して必ず維持 | 独自ドメインが外れるのを防ぐ |
| `ads.txt` | ルート直下で維持 | 広告サービスの認証を維持 |
| `app-ads.txt` | ルート直下で維持 | AdMob等のアプリ広告認証を維持 |
| `google*.html` | ファイル名・内容を変えず維持 | Google所有権確認を維持 |
| `cocktail/` | パスごと維持 | 既存ページと外部リンクを壊さない |
| `movie/` | パスごと維持 | 既存ページと外部リンクを壊さない |
| `unity/` | パスごと維持 | 既存ページと外部リンクを壊さない |
| `index.html` | 新サイト版へ置換 | TOPページ刷新 |
| `sitemap.xml` | 新旧URLを確認して統合 | 検索エンジンへ正しいURLを通知 |
| `robot.txt` | 内容を確認し、標準名 `robots.txt` と整理 | クロール設定の取りこぼしを防ぐ |

## 1. 作業前の確認

1. GitHub Pagesの公開元が `main / root` であることをSettingsで確認する。
2. Custom domain、Enforce HTTPS、Actionsの設定を記録する。
3. `CNAME`、DNS設定、`ads.txt`、`app-ads.txt`、Google認証ファイルの内容を保存する。
4. 現在のTOPと `cocktail/`、`movie/`、`unity/` の代表ページを開き、正常表示を記録する。
5. 現在の公開URL一覧を `sitemap.xml` とリポジトリ構成から作る。

## 2. 旧サイトの完全バックアップ

バックアップは次の3系統を作る。

1. GitHub上に `backup/legacy-site-YYYYMMDD` ブランチを作成する。
2. 同じコミットへ `legacy-site-YYYYMMDD` タグを付ける。
3. PCへリポジトリのミラーコピーとGit bundleを保存する。

追加で、公開中ファイルだけのZIPも保存する。バックアップ後は、ブランチ・タグ・ローカルbundleの3つから同じコミットを参照できることを確認する。

## 3. 刷新用ブランチの作成

1. 最新の `main` から `renewal/dekirukana-makaizo` ブランチを作る。
2. 新サイト側で `npm run build` と `npm run check` を実行する。
3. 新サイトの `dist/` から以下を刷新ブランチのルートへ配置する。
   - `index.html`
   - `assets/`
   - `articles/`
   - `games/`
   - `robots.txt`
   - `sitemap.xml`
4. 既存の `CNAME`、広告・Google認証ファイル、3つの既存フォルダは削除しない。
5. サイト更新用のソースコードは、公開ファイルと混同しないようリポジトリ内の `site-source/` へ置くか、別のソース管理リポジトリに置く。

## 4. 公開前調整

1. `site.config.json` のURLを実際の公開ドメインへ変更する。
2. canonical、OGP、構造化データ、sitemapのURLを再生成する。
3. `robots.txt` と旧 `robot.txt` の内容を比較し、必要なルールを統合する。
4. 旧TOPから消えるURLがある場合は、可能な範囲で転送または案内ページを用意する。
5. 個別ゲームのGoogle Play URL、公開日、画像、実績値を確定情報へ更新する。

## 5. 公開前テスト

ローカルと刷新用ブランチで次を確認する。

- PC 1440px、タブレット、iPhone 390px、Android 360px
- TOP、記事3ページ、ゲーム6ページ
- ヘッダー、モバイルメニュー、ページ内リンク
- `cocktail/`、`movie/`、`unity/` の既存URL
- `CNAME` と独自ドメイン
- `ads.txt`、`app-ads.txt`、Google認証ファイルへの直接アクセス
- 404、HTTPS、favicon、OGP
- `npm run build` と `npm run check`
- ブラウザコンソールエラーがないこと

## 6. 本番公開

1. 刷新用ブランチの差分を確認する。
2. 「残すべき既存ファイルが削除対象になっていない」ことを最終確認する。
3. `main` へマージする。
4. GitHub Pagesのデプロイ完了を待つ。
5. 公開URLでTOPと重要ファイルを再確認する。
6. Search ConsoleでURL検査を行い、更新したsitemapを送信する。

本番反映はアクセスの少ない時間帯に行う。公開完了までは旧サイトのバックアップブランチ・タグを削除しない。

## 7. ロールバック

問題があった場合は、新サイトの公開コミットを `git revert` して旧サイトへ戻す。履歴を消す操作や強制pushは使用しない。

戻した後に、GitHub Pagesの再デプロイ、独自ドメイン、広告認証ファイル、既存サブサイトを再確認する。原因修正は刷新用ブランチで行い、再テスト後に改めて公開する。

## 実施時の停止ポイント

次の3地点で作業を止め、確認を取る。

1. 旧サイトのバックアップ作成完了後
2. 刷新用ブランチの差分・プレビュー完成後
3. `main` へ反映する直前

これにより、バックアップだけを先に完了し、本番公開は別日に実施できる。
